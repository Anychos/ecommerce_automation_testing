# 1. Общая оценка

- **Текущий уровень:** **Junior AQA**

- **Общее впечатление:** Это полноценный фреймворк для автоматизации, а не набор учебных скриптов. Он демонстрирует практический опыт тестирования API на Python, но несколько пробелов в покрытии, жизненном цикле данных и качестве свидетельств не позволяют поставить оценку **Strong Junior**.

- **Что уже выглядит профессионально:** Предметно-ориентированные клиенты, централизованная конфигурация HTTP, Pydantic DTO, фабричные фикстуры, отчеты Allure, безопасные вложения cURL, явные проверки ответов, параметризованные негативные тесты и рабочий интеграционный набор.

### Статус валидации

- **ПОДТВЕРЖДЕНО ТЕКУЩЕЕ:** Собрано 57 API-тестов.

- **ПОДТВЕРЖДЕНО ТЕКУЩЕЕ:** `57 пройдено, 0 упало, 2 предупреждения` против `http://localhost:8080/`, запуск последовательный, без перезапусков или `xdist`.

- **ПОДТВЕРЖДЕНО ТЕКУЩЕЕ:** Локальная OpenAPI содержит 40 операций; реализованные клиенты представляют 22.

- **ПОДТВЕРЖДЕНО ТЕКУЩЕЕ:** `compileall`, `pip check` и `git diff --check` проходят.

- **НЕИЗВЕСТНО:** Точный коммит текущего запущенного API-целевого объекта не был проверен.

- **ВАЖНО:** Зеленый прогон доказывает, что реализованные сценарии работают с текущим целевым объектом. Это не доказывает достаточную безопасность, состояние или покрытие конечных точек.

Фреймворк имеет соответствующую своему размеру слоистую структуру:

```

Tests

  → фикстуры и фабрики

    → доменные API-клиенты

      → BaseAPIClient / HTTPX

        → целевой API

```

Отдельный слой бизнес-сервисов или репозиториев в настоящее время не требуется. Введение его сейчас в основном добавило бы церемониальности. Он может стать полезным позже для повторно используемых рабочих процессов оплаты и доставки.

# 2. Сильные стороны

- API-уровень имеет четкую доменную структуру: аутентификация, пользователи, товары, корзины и заказы разделены на клиенты, схемы, фикстуры и проверки.

- HTTP-глаголы и завершение работы клиента централизованы в [base_client.py](src/api/clients/base_client.py#L7).

- Базовый URL и конфигурация таймаута применяются централизованно. Авторизованные строители также закрывают временный клиент аутентификации в `finally` и устанавливают токен носителя на результирующий клиент в [private_builder.py](src/api/clients/private_builder.py#L9).

- Тесты не вызывают HTTPX напрямую. Детали транспорта API скрыты за доменными клиентами.

- Фикстуры с областью действия функции обеспечивают хорошую изоляцию по умолчанию. Фабрики пользователей и товаров отслеживают множество созданных сущностей и агрегируют ошибки очистки вместо остановки после первого сбоя очистки.

- Модели фикстур сохраняют как данные запроса, так и ответа, делая ожидаемые значения явными и пригодными для повторного использования в последующих проверках.

- Тесты читаемы с точки зрения QA: запрос, действие, проверка статуса, разбор ответа и бизнес-проверки визуально разделены.

- Позитивное покрытие включает полные потоки для регистрации/входа, CRUD пользователей, CRUD товаров, операции с корзиной и создание/получение заказов.

- Негативное покрытие не является поверхностным. Оно охватывает неверные форматы email, пароля и телефона, дублирующихся пользователей, недоступные товары, недостаточный запас, пустые корзины и неверные поля товаров.

- Параметризация используется там, где это улучшает покрытие без дублирования тел тестов.

- Проверки корзины и заказа сравнивают возвращенные позиции и денежные итоги с независимо подготовленными данными фикстур. Текущая реализация больше не сравнивает поля ответа сами с собой в [cart.py](src/api/tools/assertions/cart.py#L28) и [order.py](src/api/tools/assertions/order.py#L14).

- Структурированные ошибки API представлены с помощью переиспользуемых Pydantic-схем с псевдонимами в [error_schemas.py](src/api/clients/error_schemas.py#L6).

- Шаги Allure, метки feature/story, серьезность и вложения cURL облегчают расследование сбоев.

- Конфиденциальные заголовки, параметры запроса и значения JSON маскируются перед добавлением команд cURL в [curl.py](src/api/tools/http/curl.py#L30).

- Последовательный прогон без повторений является более сильным сигналом, чем выполнение с включенными по умолчанию повторными запусками.

# 3. Проблемы, снижающие зрелость проекта

## Проблема: Большая часть текущего API-контракта не представлена

Текущая OpenAPI предоставляет 40 операций. Существующие клиенты аутентификации, пользователей, товаров, корзин и заказов представляют 22. Остальные 18 включают health, платежи, доставки, связанные веб-хуки и операции оплаты/доставки заказов.

В то же время [payments/client.py](src/api/clients/payments/client.py#L4) и [deliveries/client.py](src/api/clients/deliveries/client.py#L4) содержат пустые публичные классы с `pass`.

### Почему это важно:

Пустые доменные пакеты делают проект незавершенным. Интервьюер не может сказать, запланированы ли эти домены, заброшены или ошибочно заявлены как поддерживаемые. Переходы состояний платежей и доставки также являются одними из наиболее ценных сценариев API для электронной коммерции.

### Рекомендация:

Выберите явную область действия:

1. Перед публикацией удалите пустые заглушки и задокументируйте, что покрытие портфолио заканчивается созданием заказа; или

2. Реализуйте один узкий поток оплаты и доставки, используя конечные точки API с фейковым провайдером:

   - создать платеж → успех → получить/синхронизировать;

   - запросить котировку → создать доставку → перевести в состояние доставлено;

   - добавить по одному тесту на неверный переход состояния для каждого домена.

Не пытайтесь охватить все варианты веб-хуков только для увеличения количества конечных точек.

### Приоритет:

**Высокий**

В текущем дереве нет каталога `tests/unit`. Тем не менее:

### Почему это важно:

Это наносит больший ущерб на собеседовании, чем открыто отсутствующая функция. Это создает сомнения в том, можно ли доверять тестовым свидетельствам, статусам выполнения и опубликованным результатам.

Интеграционный прогон доказывает, что текущие проверки приняли реальный ответ API. Это не доказывает независимо, что каждое мутированное поле было бы отклонено.

### Рекомендация:

Приведите документацию в соответствие с репозиторием:

- Восстановите и закоммитьте заявленные целенаправленные модульные тесты; или

- Удалите утверждения и заново откройте соответствующие пункты контрольного списка.

Полезная область модульного тестирования невелика:

- делегирование `BaseAPIClient.close()`;

- очистка private-builder при успешном или неудачном входе;

- очистка пользователя/товара после сбоя теста и после уже удаленной сущности;

- мутационные проверки полей корзины/заказа, итогов, статусов и списков позиций.

## Проблема: Некоторые тесты успешного создания обходят фабрики очистки

Примеры включают:

- регистрацию в [test_authentication.py](tests/api/test_authentication.py#L35);

- прямое создание пользователя в [test_user.py](tests/api/test_user.py#L38);

- прямое создание товара в [test_product.py](tests/api/test_product.py#L41);

- прямое создание корзины в [test_cart.py](tests/api/test_cart.py#L38).

У фабрик пользователей и товаров есть реестры очистки, но сущности, созданные непосредственно этими тестами, там не регистрируются. Очистка корзины/заказа также может зависеть от удаления владельца-пользователя или от поведения каскадного удаления на бэкенде.

### Почему это важно:

Набор тестов может проходить, но при этом загрязнять окружение. Накопленные данные впоследствии могут вызывать сбои из-за дублирования данных, замедление запросов списков, вводящие в заблуждение результаты покрытия или периодические сбои при параллельном запуске.

### Рекомендация:

Организуйте создание успешных сущностей через отслеживаемые фабрики, сохраняя при этом видимость фактического вызова конечной точки в тесте:

- Позвольте реестру очистки принимать сущность, созданную тестом.

- Регистрируйте возвращенный ID сразу после успешного создания.

- Сохраняйте идемпотентность `404` во время очистки, но сообщайте обо всех других ошибках очистки.

- Документируйте, для каких ресурсов нет конечной точки удаления и какой проверенный каскад на бэкенде отвечает за их очистку.

### Приоритет:

**Высокий**

## Проблема: Покрытие аутентификации, авторизации и владения ресурсами слабое

Набор тестов проверяет сбои входа, но безопасность защищенных ресурсов в значительной степени отсутствует. Почти нет или совсем нет покрытия для:

- отсутствующих, некорректных или просроченных токенов носителя;

- обычного пользователя, вызывающего операции администратора с пользователями/товарами;

- пользователя А, обращающегося к заказу пользователя Б;

- идентификаторов корзины или заказа, принадлежащих другому пользователю;

- попыток повышения привилегий через `is_admin`;

- токенов удаленного пользователя.

### Почему это важно:

Для коммерческого тестирования API аутентификация — это не только конечная точка входа. Контроль доступа и владение объектами являются высокорисковым бизнес-поведением, особенно для пользователей, корзин, заказов, платежей и доставок.

### Рекомендация:

Добавьте компактную матрицу ролей/доступа вместо дублирования каждого маршрута:

- неаутентифицированный запрос → `401`;

- аутентифицированный пользователь, вызывающий административную операцию → `403`;

- пользователь А, запрашивающий сущность пользователя Б → соответствующее контракту `403` или `404`;

- административная операция → успех;

- удаленный или недействительный токен → отклонен.

Отдайте предпочтение репрезентативным операциям для каждого правила авторизации, а не механическому тестированию каждой конечной точки.

## Проблема: Валидация контракта ответа дублируется, но не является независимой

Тесты сначала разбирают ответы с помощью Pydantic, а затем проверяют те же необработанные JSON-данные на соответствие JSON-схеме, сгенерированной из этой Pydantic-модели. Например, этот шаблон встречается в [test_order.py](tests/api/test_order.py#L48).

Модели Pydantic по умолчанию также игнорируют неожиданные поля, если не настроено иное. Поэтому сгенерированная схема не обязательно отклоняет необъявленные свойства ответа.

### Почему это важно:

Второе утверждение выглядит как независимое покрытие контракта, но обе валидации исходят из одной и той же локальной модели. Оно не может выявить ошибку, общую для модели и проверки, и не является проверкой по опубликованному OpenAPI-контракту.

### Рекомендация:

Выберите одну четкую стратегию:

- Используйте строгие Pydantic-модели ответов с `extra="forbid"` и удалите повторяющуюся локальную валидацию JSON-схемы; или

- Проверяйте выбранные ответы на соответствие схемам ответов, извлеченным из фиксированного OpenAPI-документа.

Для этого проекта строгие Pydantic-модели являются более простым выбором по умолчанию. OpenAPI-валидация может оставаться отдельным контрактным тестом или отчетом о покрытии.

### Приоритет:

**Средний**

## Проблема: Интерфейс клиента не согласован

Некоторые доменные методы возвращают необработанный `httpx.Response`; некоторые дополнительно имеют типизированные обертки, такие как `login()`, `create_user()` или `create_order()`. Тесты обычно используют необработанные методы, чтобы сначала проверить статус, в то время как фикстуры часто используют типизированные обертки.

Строители аутентификации разбирают ответ входа без предварительной генерации четкого HTTP-сбоя. Неверные учетные данные могут поэтому проявиться как ошибка разбора Pydantic вместо действенной ошибки аутентификации.

### Почему это важно:

Новому тестировщику приходится выбирать между двумя соглашениями для каждой операции. Непоследовательное поведение при сбоях также затрудняет диагностику проблем с окружением или учетными данными.

### Рекомендация:

Для фреймворка тестирования API предпочтите одно простое соглашение:

- Методы конечных точек возвращают `Response`.

- Тесты или общие вспомогательные функции разбора проверяют ожидаемый статус, а затем валидируют соответствующую Pydantic-модель.

- Настройка аутентификации явно проверяет статус входа и включает в себя сводку ответа с замаскированными данными в случае сбоя настройки.

- Добавьте перехватчик ответа, который прикрепляет метод, URL, статус, затраченное время и безопасно замаскированное тело к Allure.

Не вызывайте `raise_for_status()` глобально, потому что негативные тесты намеренно работают с ответами `4xx`.

### Приоритет:

**Средний**

## Проблема: Повторы по умолчанию и параллельное выполнение могут скрывать дефекты жизненного цикла

[pytest.ini](pytest.ini#L3) включает два автоматических повтора и два рабочих процесса xdist для каждого обычного вызова.

Текущий последовательный прогон проходит без повторов, что является положительным моментом. Однако конфигурация по умолчанию все еще позволяет сообщать о нестабильной первой попытке как об успешной.

### Почему это важно:

Повторы полезны для диагностики, но они не должны становиться определением успеха. Параллелизм также следует включать только после того, как будет продемонстрирована безопасность изоляции ресурсов.

### Рекомендация:

Используйте детерминированные настройки по умолчанию:

- локальная/диагностическая команда: последовательно, без повторов;

- явная команда для параллельного запуска: `-n 2`;

- опциональное задание с повторами или маркер для известной внешней нестабильности;

- сохраняйте информацию о сбое при первой попытке в отчетах.

### Приоритет:

**Средний**

## Проблема: Некоторые негативные сценарии являются недетерминированными или неверно обозначены

В сценарии с несуществующим товаром используется жестко заданный ID `1001` в [test_cart.py](tests/api/test_cart.py#L138). Этот ID может в конечном итоге существовать в постоянном окружении.

Некоторые тесты "отсутствующего обязательного поля" отправляют пустые строки или ноль вместо фактического опускания поля. Это допустимые негативные случаи, но они проверяют другие правила валидации.

Два предупреждения времени выполнения также возникают из-за сериализации целочисленных значений через поля Pydantic, объявленные как строки.

### Почему это важно:

Негативные тесты должны контролировать свои предусловия. В противном случае тест может изменить свое значение по мере роста базы данных. Неверные заголовки тестов также ослабляют прослеживаемость между сценарием и проверяемым правилом.

### Рекомендация:

- Создайте и удалите ресурс, затем используйте его реальный удаленный ID для детерминированного покрытия `404`.

- Тестируйте опущенные поля с помощью явных сырых словарей.

- Разделяйте случаи с пустыми, нулевыми, неверного типа и отсутствующими полями.

- Используйте сырые словари полезной нагрузки или небольшой построитель неверной полезной нагрузки для намеренно недействительных с точки зрения схемы запросов, вместо того чтобы пропускать их через допустимые DTO запросов.

### Приоритет:

**Средний**

## Проблема: Модели ответов могли бы более точно описывать контракты

Несколько значений используют широкие типы:

- временные метки являются строками;

- статусы являются неограниченными строками;

- URL являются строками;

- денежные значения являются числами с плавающей точкой.

Также есть неиспользуемые импорты, длинные импорты с обратными слешами и строки документации, которые повторяют имена методов без добавления поведенческой информации.

### Почему это важно:

Точные типы ответов позволяют раньше выявлять отклонения контракта. Полировка кода также заметна во время собеседования по портфолио, хотя это менее важно, чем корректные тесты.

### Рекомендация:

После подтверждения OpenAPI-контракта:

- используйте `datetime` для временных меток;

- используйте `Literal` или небольшие перечисления для стабильных статусов;

- используйте типы URL, где API гарантирует URL;

- рассмотрите `Decimal` только в том случае, если контракт API предоставляет безопасную для десятичных чисел семантику денежных значений;

- удалите неиспользуемые импорты и оставляйте строки документации только там, где они объясняют поведение, очистку или неочевидные ограничения.

### Приоритет:

**Низкий**

# 4. Отсутствующие функции для сильного портфолио Junior AQA

Следующие дополнения обеспечили бы реальную ценность для собеседования:

1. **Целенаправленное покрытие авторизации**

   - `401`, `403`, владение/IDOR, недействительный токен, удаленный пользователь.

   - Это самый важный недостающий навык проектирования тестов.

2. **Независимые модульные тесты фреймворка**

   - Мутационные тесты проверок, закрытие клиента и поведение очистки.

   - Они демонстрируют, что тестируется сам фреймворк, а не только приложение.

3. **Детерминированное покрытие граничных значений**

   - Количество `0`, отрицательное и точное граничное значение запаса.

   - Отрицательная цена и запас.

   - Фактически отсутствующие поля по сравнению с пустыми значениями.

   - Несуществующие и удаленные ресурсы.

   - Неверное состояние для межпользовательских операций.

4. **Один рабочий процесс оплаты и доставки**

   - Узкий поток с фейковым провайдером продемонстрировал бы тестирование API с учетом состояния без излишней сложности внешней интеграции.

5. **Честный отчет о покрытии OpenAPI**

   - Отчет о покрытых и непокрытых операциях из фиксированной спецификации.

   - Не представляйте наличие декораторов как измеренное покрытие.

6. **Точная тестовая документация**

   - Каждая документированная команда и тестовый артефакт должны существовать в опубликованном репозитории.

   - Фиксируйте целевую ревизию при каждом утверждении воспроизводимого интеграционного результата.

Такие функции, как общий шаблон репозитория, контейнер внедрения зависимостей, пользовательский HTTP-фреймворк или сложный сервисный слой, не являются необходимыми для этого портфолио.

# 5. Рекомендации по рефакторингу

## Перед публикацией:

1. Восстановите заявленные модульные тесты фреймворка API или удалите все ложные утверждения о `tests/unit` и мутационных тестах.

2. Регистрируйте каждого успешно созданного пользователя, товар и корзину для детерминированной очистки, включая ресурсы, созданные непосредственно внутри позитивных тестов.

3. Добавьте небольшой набор тестов контроля доступа, охватывающих неаутентифицированные, запрещенные и межпользовательские запросы.

4. Удалите пустые заглушки платежей/доставки или реализуйте один связный поток оплаты и доставки.

5. Замените проверки JSON-схемы, основанные на самодеривированных данных, строгой Pydantic-валидацией или действительно независимой проверкой по фиксированному OpenAPI-контракту.

6. Сделайте соглашение о сырых и типизированных клиентах единообразным и улучшите диагностику настройки аутентификации.

7. Сделайте последовательное выполнение без повторов командой валидации портфолио по умолчанию.

8. Закоммитьте текущие улучшения API как согласованные изменения перед представлением репозитория.

## Желательно:

1. Усильте типизацию временных меток, статусов, URL, параметров запроса и денежных значений после проверки реального контракта.

2. Очистите неиспользуемые импорты, повторяющиеся строки документации, длинные строки и два предупреждения о сериализации намеренно неверной полезной нагрузки.
